# 终端优化回归：根因、验证与预防

本轮最终交付为 0.3.7（`03fc571`）。用户明确反馈“以上问题都验证通过”（reported），作为本轮验收确认（approved）；自动化测试、安装文件与运行参数检查属于 observed。当前行为以 [API 契约](../api-contract.md) 和 [工程维护要求](../engineering.md) 为准。本记录保存可复用经验，不把用户手工验证写成自动化端到端测试。

## 1. 已确认的应用缺陷

| 问题 | 根因与修复 | 必须保留的验证边界 |
| --- | --- | --- |
| Agent 空白、Codex CLI 无法打开 | Agent runtime 直接进入 store，绕过普通终端的输出消费者注册；后端等消费者、前端等首段输出，最终超时。`beginLiveOutput` 主动注册消费者，保留原启动路径 | 普通终端、Agent、已有 session、切换与关闭都要覆盖；不能只测通用打开函数 |
| 已连接但关联信息不正确 | 连接显示需要独立于 Agent 打开结果解析，优先保存的连接名称 | saved name 与自定义标签标题不同、Agent 打开尚未完成时仍显示关联连接；只保留一行连接信息 |
| rz 达到 100% 后不返回输入 | 宽泛过滤重复启动头，误吞文件完成后的 `ZRINIT`；取消选择在 `ZACK` 状态误用正常 close | 仅上传选择/读取阶段过滤重复初始头；结束握手交给协议库；取消使用 abort；字节进度完成不等于会话关闭 |
| sz 报 `Unhandled header: ZRQINIT` | 目录选择未完成时远端重发启动头，已确认的接收会话不接受它 | 同事件重复帧、跨事件分片、选择完成边界；等待结束后只续接旧部分帧，后续文件数据原样传递 |
| 关闭后输出状态遗留 | 显式关闭后 reader finalizer 遇 NotFound 提前返回，跳过清理 | 先关闭已有 flow 唤醒 reader，再由 finalizer 在 gate 排空后移除；未知/重复关闭不创建 tombstone |
| 批量传输操作失败后 UI 不一致 | Promise 拒绝未受控、重复操作、删除成功项未及时更新 | 批量与关联单任务互斥；成功项即时移除、失败项保留并可重试；不以最终一次性更新掩盖部分成功 |

证据提交：`afedb69`（Agent、上传与清理）、`b848430`（下载重传）；后者的无效原生文件框尝试已由 `5cba77e` 精确撤销，协议修复保留。

## 2. 鼠标问题：不要把时间先后当成因果

用户最初观察为“优化前正常、优化后 rz/sz 文件框鼠标不可见”，且移动鼠标仍不能恢复，其他文件框正常。这是有效线索，但不能单凭它锁定应用提交。

| 对照 | 结果及来源 |
| --- | --- |
| 优化前 `e7ce441` 程序 + 默认 WebView2 152.0.4191.66 | 仍异常（用户实测）；实际运行库路径由父子进程关系核实 |
| 同程序 + 临时指定 151.0.4129.93 + 独立 WebView 缓存 | 指针正常（用户实测）；此轮同时改变缓存，只能作为线索 |
| 同程序 + 原缓存 + 152.0.4191.66，仅禁用 `HideCursorWhileTyping` | 指针正常（用户实测）；这一轮隔离了目标开关 |
| 安装版 0.3.7 普通启动，无诊断环境变量 | 实际仍加载 152，兼容参数自动生效、原默认参数保留（工具检查）；用户随后确认全部问题通过 |

结论：本次指针异常由 WebView2 152 的键入隐藏指针行为触发；无需回滚全部优化。上游线索见 [WebView2 #5687](https://github.com/MicrosoftEdge/WebView2Feedback/issues/5687)，兼容范围与移除条件见 [工程维护要求](../engineering.md#webview2-152-指针兼容)。上游缺陷报告不能替代本机版本、参数和对照验证。

## 3. 无效尝试与审查中拦截的问题

- 仅将文件框改到 UI 主线程没有解决问题，且发生在首次故障之后，不能反过来解释最初根因；无效尝试及时撤销，不叠加补丁。
- 名称带 `blocking` 不代表在调用线程执行。Tauri dialog 的阻塞包装内部仍走异步路径，不能直接放到主线程阻塞等待；应读实际依赖版本源码。
- 两层过滤同一事件会重排暂存前缀；选择完成后继续扫描整个事件会误删文件数据。过滤只执行一次，缓存有界，跨阶段只处理旧前缀。
- Wry 的 `additional_browser_args` 会替换默认生成参数；兼容开关须合并到同一个 `--disable-features`，保留原有默认项和 autoplay。安装后检查实际子进程参数，不只检查源码字符串。
- 全文件格式化、未接入前端的新 IPC、测试绕过统一 Tauri 封装都会增加审查噪声或留下无效实现；提交前检查调用链和精确 diff。

## 4. 下次按此顺序排查和验证

1. 固定可复现症状、程序 commit/版本、实际加载的桌面运行库、触发方式及正常对照；只提取必要字段，不输出包含凭据的完整进程命令行。
2. 对照应用版本与运行库版本，逐次只改一个因素。旧应用也失败时，继续检查共同依赖和环境，不继续以“刚改过”证明因果。
3. 先建立能在旧代码上失败的回归，再做最小修复；首选原有入口，撤销被实测否定的尝试。
4. 协议使用真实 `zmodem.js` 双端测试，验证全部字节、结束握手及普通输出恢复；同时覆盖分片、合并、取消、失败、关闭及过期回调。Mock 适合 UI/IPC 契约，不能独自证明互操作成功。
5. 桌面现象用实际安装版验证。Headless MCP 不具备 GUI 操作能力时保留缺口，由用户实测补证；不得绕过 SSH 统一入口，也不得将 `/usr/bin/rz` 存在或单测通过当作完整传输验收。
6. 打包后将安装文件与安装包内 payload 比较；Tauri 会按 bundle 类型修补 exe，不能仅比较未打包的 release 源文件。再核对注册版本、实际启动路径、运行库与目标参数。
7. 先独立审查、后提交安装；区分代码修复、测试通过、安装检查和用户验收。后续修改仍须重做受影响的验证，不能沿用本轮结论。
